# 阶段二第 20～25 天完整计划

## 总体目标

前 19 天已经完成：

```text
Runtime 基础
→ 状态机与调度
→ 并行执行与预算
→ Timeout / Cancellation
→ RunCoordinator
→ Model Routing / Retry / Circuit Breaker
→ Runtime Event
→ Tool Execution Contract
→ RAG / Memory Runtime Contract
→ Event Journal / Idempotency
```

后 6 天不再继续扩展新的 Agent 能力，而是完成生产级闭环：

```text
Observability
→ Trace
→ Snapshot / Recovery Validation
→ 真实 API E2E 迁移
→ Fault Injection
→ 最终验收与项目总结
```

## 后续阶段统一原则

1. 优先复用已有 `RuntimeEvent` 和 Event Journal（事件日志），不创建第二套事实来源。
2. 日志、指标和 Trace（链路追踪）只能观察 Runtime，不能修改 Run/Step 状态。
3. Snapshot（快照）与 Journal 暂不构成完整 Event Sourcing（事件溯源）系统。
4. Replay（回放）不得重新调用真实 Model、Tool 或 RAG。
5. 第 23 天必须迁移真实 API 路径，不能继续只保留测试旁路。
6. 第 24 天故障注入必须是确定性的，不能依赖随机概率。
7. 第 25 天不新增大型功能，只允许测试、文档和必要的小范围修复。
8. 若某天实际需要修改 Tool Call（工具调用）执行逻辑，按照既定规则暂停当天学习，先单独准备复杂模拟 Tool；仅集成现有 Tool 路径不触发该规则。

# 第 20 天：Observability、Structured Logging 与 Runtime Metrics

## 一、学习主题

- Observability（可观测性）的三大支柱：
  - Logging（日志）
  - Metrics（指标）
  - Trace（链路追踪，第 21 天展开）
- Structured Logging（结构化日志）
- Counter（计数器）
- Gauge（仪表）
- Histogram（直方图）
- Event-driven Metrics（事件驱动指标）
- Idempotent Metrics Consumption（幂等指标消费）
- High Cardinality（高基数）问题
- Label Policy（标签策略）
- Sensitive Data Redaction（敏感数据脱敏）
- Observability Failure Isolation（可观测性故障隔离）

## 二、核心架构

不在各组件中重复散落打点，统一采用：

```text
RuntimeEvent
→ Observability Consumer
├── Structured Runtime Logger
└── Runtime Metrics Recorder
```

主要事实来源仍然是：

```text
RuntimeEvent / Event Journal
```

Logger 和 Metrics Recorder 不自行推断或修改 Runtime 状态。

## 三、LocalAgent 改造目标

### 1. Structured Runtime Logger

统一结构化字段：

```text
timestamp
level
run_id
trace_id
step_id
component
event_id
event_type
status
error_code
retry_index
duration_ms
```

可选的低风险字段：

```text
model_profile
tool_name
retrieval_stage
cancellation_reason
side_effect_state
retry_disposition
```

不得记录：

- 用户正文
- Prompt
- Model Messages
- Tool 参数和输出正文
- RAG Chunk
- Memory 正文
- API Key
- Provider 原始响应
- Traceback
- 本地敏感路径

日志应使用安全投影，不直接序列化 Runtime 对象。

### 2. Metrics Recorder

建立统一接口，例如：

```text
RuntimeMetricsRecorder
InMemoryMetricsRecorder
NoopMetricsRecorder
```

不要求接入真实 Prometheus（普罗米修斯）服务，但接口设计应兼容未来 Exporter（导出器）。

### 3. Counter 指标

至少包括：

```text
runtime_runs_total
runtime_steps_total
runtime_model_attempts_total
runtime_tool_attempts_total
runtime_retrievals_total
runtime_retries_total
runtime_budget_exhaustions_total
runtime_timeouts_total
runtime_cancellations_total
runtime_journal_append_failures_total
runtime_event_duplicates_total
runtime_observability_dropped_records_total
```

### 4. Gauge 指标

至少包括：

```text
runtime_active_runs
runtime_active_steps
runtime_detached_tool_workers
runtime_detached_retrieval_workers
runtime_blocking_executor_active
runtime_blocking_executor_pending
runtime_event_channel_buffered
runtime_circuit_breakers_open
```

### 5. Histogram 指标

至少包括：

```text
runtime_run_duration_seconds
runtime_step_duration_seconds
runtime_model_duration_seconds
runtime_tool_duration_seconds
runtime_retrieval_duration_seconds
runtime_journal_append_duration_seconds
runtime_blocking_executor_wait_seconds
```

### 6. 高基数治理

以下字段禁止作为 Metrics Label：

```text
run_id
trace_id
event_id
step_id
invocation_id
retrieval_id
query_digest
resource_key_digest
source_id
chunk_id
用户输入
文件路径
```

可作为 Label 的字段必须来自有限枚举：

```text
component
event_type
status
error_code
model_profile
retry_disposition
retrieval_stage
cancellation_reason
```

`tool_name` 仅在 Tool 集合有限且受控时允许作为 Label。

### 7. 幂等指标消费

第 19 天已经支持重复 Event，因此 Metrics Consumer 必须基于：

```text
event_id
```

进行幂等处理。

同一 Event：

```text
实时消费一次
+ 未来 Journal 重投一次
```

不能让 Counter 增加两次。

优先复用 `IdempotentEventConsumer` 或同等级消费机制，不创建第三套无约束去重逻辑。

### 8. 可观测性故障隔离

Logger 或 Metrics Recorder 失败时：

- 不改变 RunStatus；
- 不改变 StepStatus；
- 不重新调用 Model、Tool、RAG；
- 不触发业务 Retry；
- 不阻塞 Runtime 无限等待；
- 记录 Dropped Record 指标；
- 保持安全降级。

## 四、主要产出

- Structured Runtime Logger
- Event-driven Metrics Recorder
- Idempotent Observability Consumer
- Metrics Naming Convention
- Metrics Label Policy
- Sensitive Data Redaction Policy
- Observability Failure Isolation
- `day20_observability_result.md`

## 五、重点 Bad Case

1. 同一 Event 被重复消费，Counter 增加两次。
2. `run_id` 被作为 Label，造成高基数。
3. Tool Output 被写入结构化日志。
4. Metrics Exporter 失败导致 Run 失败。
5. Gauge 增加后异常退出，未正确减回。
6. `RUN_COMPLETED` 重复事件导致 Run 总数重复。
7. Logger 使用 `repr(exception)` 泄漏原始异常。
8. Model Retry 被同时按 Invocation 和 Attempt 重复计数。
9. Journal Event 与实时 Event 分别打指标。
10. Histogram 单位混用毫秒和秒。
11. Cancellation 被统计为普通 Failure。
12. Observability Consumer 阻塞 EventChannel。

## 六、验收重点

- 指标只由安全 Runtime Event 投影生成；
- 重复 Event 不重复计数；
- 日志与 Event 的身份字段一致；
- Counter、Gauge、Histogram 类型使用正确；
- 无高基数用户 Label；
- Logger/Metrics 故障不改变业务结果；
- 不保存敏感正文；
- 全仓测试通过。

# 第 21 天：Trace、Span 与调用链传播

## 一、学习主题

- Trace（链路追踪）
- Span（跨度）
- Span Context（跨度上下文）
- Parent / Child Span
- Root Span
- Invocation Span 与 Attempt Span
- Async Context Propagation（异步上下文传播）
- Thread Context Propagation（线程上下文传播）
- TaskGroup 并行 Span
- Error / Timeout / Cancellation Attributes
- Trace 与日志、指标关联
- OpenTelemetry（开放遥测）兼容接口

## 二、目标调用树

```text
Run Span
├── Planner Span
├── Step Span A
│   ├── Model Invocation Span
│   │   ├── Model Attempt Span 0
│   │   └── Model Attempt Span 1
│   ├── Tool Invocation Span
│   │   ├── Tool Attempt Span 0
│   │   └── Tool Attempt Span 1
│   └── Retrieval Span
│       ├── Query Rewrite Span
│       ├── Embedding Span
│       ├── Retrieve Span
│       ├── Rerank Span
│       ├── Document Load Span
│       └── Context Build Span
└── Step Span B
```

## 三、LocalAgent 改造目标

### 1. 复用现有 trace_id

不得重新创建一套与 RunContext 无关的 trace ID。

```text
RunContext.trace_id
→ 全 Run Trace 根身份
```

每个 Span 生成独立 `span_id`。

### 2. Trace Context

建议建立：

```text
TraceContext
SpanContext
SpanRecord
SpanRecorder
```

至少包含：

```text
trace_id
span_id
parent_span_id
run_id
step_id
component
operation
started_at
completed_at
status
error_code
```

### 3. Span 层级

需要区分：

```text
逻辑 Invocation
→ 多次 Attempt
```

Model、Tool 的 Retry 不得生成彼此无关的根 Span。

正确关系：

```text
Model Invocation Span
├── Attempt 0
└── Attempt 1
```

### 4. TaskGroup 传播

并行 Step 使用兄弟 Span：

```text
Run Span
├── Step A Span
├── Step B Span
└── Step C Span
```

不能把 Step B 错误设置为 Step A 的子 Span。

### 5. BoundedBlockingExecutor 传播

第 18 天的同步 Worker 必须继承：

- trace_id
- parent span_id
- run_id
- step_id
- component

可通过：

```text
显式 TraceContext
```

或：

```python
contextvars.copy_context()
```

实现。

不能假设自建线程池会自动传播所有 ContextVar。

### 6. Span Attributes

允许记录：

```text
component
operation
status
error_code
retry_index
model_profile
retrieval_stage
budget_usage
timeout_reason
cancellation_reason
side_effect_state
```

不得记录：

- Prompt
- 用户正文
- Model Output
- Tool 参数
- Tool Output
- RAG Chunk
- Memory
- Secret
- canonical path

### 7. Trace 与 Logging / Metrics 关联

日志可以包含：

```text
trace_id
span_id
```

但 `span_id` 和 `trace_id` 禁止作为 Metrics Label。

Trace 观察 Runtime 生命周期，不负责决定组件终态。

### 8. OpenTelemetry 兼容边界

建议提供：

```text
NoopSpanRecorder
InMemorySpanRecorder
OpenTelemetryCompatibleSpanAdapter
```

不要求：

-部署 Collector；
-部署 Jaeger；
-接入云端 Trace；
-引入复杂生产依赖。

### 9. Recorder 故障隔离

Span Recorder 或 Exporter 失败：

- 不改变业务结果；
- 不阻止 Span 对应的 Runtime 组件结束；
- 不重新执行操作；
- 记录 Dropped Span 指标；
- 所有 Span 本地状态必须最终关闭。

## 四、主要产出

- Trace Context
- Span Record / Span Recorder
- Run / Step / Invocation / Attempt Span 层级
- Async Context Propagation
- Thread Context Propagation
- OpenTelemetry-compatible Adapter
- 调用树测试
- 并行 Span 测试
- `day21_trace_result.md`

## 五、重点 Bad Case

1. Retry Attempt 成为新的根 Trace。
2. 并行 Step 被错误串成父子关系。
3. Worker Thread 丢失 trace_id。
4. Timeout 后 Span 一直不结束。
5. Cancelled Span 被标记为普通 Success。
6. Span 中写入 Prompt。
7. Trace Exporter 失败导致 Run FAILED。
8. 同一 Runtime Event 创建两个 Span。
9. Span Recorder 成为生命周期 Owner。
10. Tool Detached Worker 结束后重新修改已关闭 Span。
11. Trace ID 与日志 Trace ID 不一致。
12. Span ID 被作为 Metrics Label。

## 六、验收重点

- Run 只有一个 Root Span；
- Step Span 层级正确；
- Invocation / Attempt 分层正确；
- TaskGroup 子任务继承 Trace；
- Blocking Executor 继承 Trace；
- Cancel、Timeout、Error Span 正确收口；
- 所有 Span 最终关闭；
- Trace 不包含敏感正文；
- Recorder 失败不改变业务结果；
- 日志、Event、Trace 身份一致。

# 第 22 天：Snapshot、Checkpoint、Recovery Validation 与受限 Replay

## 一、学习主题

- Snapshot（快照）
- Checkpoint（检查点）
- Snapshot Barrier（快照屏障）
- Schema Version（模式版本）
- Plan Fingerprint（计划指纹）
- Recovery Validation（恢复校验）
- Recovery Assessment（恢复评估）
- Journal Tail（日志尾部）
- Limited Replay（受限回放）
- Claimed / Running Step 恢复语义
- External Side Effect Reconciliation（外部副作用对账）
- Crash Window（崩溃窗口）

## 二、重要范围调整

本日不实现完整 Replay Engine。

准确目标为：

```text
Versioned Snapshot
+ Journal Tail Validation
+ Limited State Reduction
→ Recovery Assessment
```

不宣称：

- 完整 Run Recovery；
- Event Sourcing；
- 任意 Run 自动继续；
- 完整用户输出恢复；
- Model、Tool、RAG 自动重放。

## 三、LocalAgent 改造目标

### 1. RunSnapshot

Snapshot 至少包含：

```text
snapshot_schema_version
snapshot_id
run_id
trace_id
plan
plan_fingerprint
agent_state
budget_snapshot
last_journal_sequence
run_status
stop_reason
cancellation_reason
step_states
runtime_metadata
created_at
quiescent
```

### 2. Snapshot 禁止保存

- Lock
- Semaphore
- Task
- Future
- Generator
- EventChannel
- EventEmitter
  -数据库连接
  -Model/Tool Adapter
  -Embedding 实例
  -HTTP Session
  -Prompt
  -RAG 正文
  -Memory 正文
  -Secret

### 3. Plan Fingerprint

恢复前必须验证：

```text
Snapshot.plan_fingerprint
==
当前静态 Plan 的 fingerprint
```

Plan 指纹至少覆盖：

- step ID；
  -agent / capability；
  -dependencies；
  -static input；
  -completion criteria；
  -plan version。

不得覆盖 Runtime StepStatus 等动态字段。

### 4. Snapshot Store

实现最小本地：

```text
SnapshotStore
InMemorySnapshotStore
SQLiteSnapshotStore 或 FileSnapshotStore
```

必须：

-严格版本化；
-原子写入；
-Digest 校验；
-损坏 fail closed；
-不提供静默修复。

### 5. Checkpoint Barrier

安全 Checkpoint 位置优先限定为：

- Run 尚未开始；
- Step 边界；
- Run Terminal。

Checkpoint 流程：

```text
请求 Checkpoint
→ 暂停 Claim 新 Step
→ 等待正在提交的状态完成
→ 读取 Journal Sequence 水位
→ 创建 Snapshot
→ 恢复 Scheduler
```

如果仍有运行中的 Worker：

```text
quiescent = False
```

不得把非静止 Snapshot 直接判定为可恢复。

### 6. Recovery Assessment

建议状态：

```text
TERMINAL
RESUMABLE
REQUIRES_RECONCILIATION
INCOMPATIBLE_SCHEMA
PLAN_MISMATCH
CORRUPTED
JOURNAL_GAP_OR_CONFLICT
UNSUPPORTED
```

### 7. RUNNING / CLAIMED Step

Snapshot 中发现：

```text
StepStatus.RUNNING
StepStatus.CLAIMED
```

不得直接：

-标记成功；
-重新执行；
-自动标记失败。

默认进入：

```text
REQUIRES_RECONCILIATION
```

### 8. Tool 副作用恢复

恢复评估需要检查：

- idempotency kind；
  -idempotency key；
  -side-effect state；
  -compensation state；
  -outcome unknown；
  -detached worker；
  -Journal 中的 Tool Event。

安全规则：

```text
NON_IDEMPOTENT + COMMITTED
→ 不自动重放

UNKNOWN outcome
→ 不自动重放

IDEMPOTENT_WITH_KEY + 明确 Replay
→ 可以评估为可重试候选
```

但本日不真正执行 Tool Retry。

### 9. 受限 Journal Tail Reducer

允许处理：

- Snapshot Sequence 之后的 Run/Step 终态元数据；
  -Budget 安全快照更新；
  -Cancellation/StopReason；
  -Terminal Event；
  -已知安全事件顺序校验。

不得：

-重新调用 Model；
-重新调用 Tool；
-重新执行 RAG；
-重建用户正文；
-重建 Prompt；
-自动恢复外部副作用。

### 10. Snapshot / Journal 对齐

必须验证：

```text
snapshot.last_journal_sequence
<= journal.last_sequence(run_id)
```

如果 Snapshot Sequence 高于 Journal：

```text
CORRUPTED 或 JOURNAL_GAP_OR_CONFLICT
```

如果 Journal Tail Digest 损坏：

```text
fail closed
```

## 四、主要产出

- Versioned RunSnapshot
- Snapshot Store
- Checkpoint Barrier
- Plan Fingerprint
- Recovery Validator
- Recovery Assessment
- Limited Journal Tail Reducer
- Side-effect Recovery Decision
- `day22_snapshot_replay_result.md`

## 五、重点 Bad Case

1. Snapshot 保存 Lock/Future。
2. Plan 已变化却继续恢复。
3. RUNNING Step 被直接重跑。
4. 非幂等 Tool 已提交后自动重放。
5. Snapshot Sequence 高于 Journal。
6. Snapshot 非静止却标记 RESUMABLE。
7. Corrupted Snapshot 被自动“修复”。
8. Replay 重新调用真实 Model。
9. Journal Tail 出现第二个 Terminal。
10. Snapshot Schema 不兼容仍强行读取。
11. Budget Snapshot 与 AgentState 不一致。
12. 将 Limited Replay 描述为完整 Recovery。

## 六、验收重点

- Snapshot 可严格序列化和校验；
- Plan fingerprint 稳定；
- Snapshot/Journal sequence 对齐；
  -安全位置生成 Quiescent Snapshot；
- RUNNING/CLAIMED 不自动重跑；
- Outcome Unknown 进入人工对账；
- Replay 不调用真实 Model/Tool/RAG；
  -损坏数据 fail closed；
  -不宣称完整 Event Sourcing。

## 七、代码实操

**需要，工作量较大。**

# 第 23 天：End-to-End Runtime Integration 与默认入口迁移

## 一、学习主题

- End-to-End（端到端）生命周期
- Component Integration（组件集成）
- Runtime Mode Selection（运行时模式选择）
- Feature Flag（功能开关）
- Legacy Migration（遗留路径迁移）
- Compatibility Boundary（兼容边界）
- Shutdown Lifecycle（关闭生命周期）
- Graceful Shutdown（优雅关闭）
- Happy Path / Failure Path
- 完整终态保证

## 二、核心目标

至少将一条真实用户 API 链路迁移为：

```text
UI / API
→ ChatService
→ RunCoordinator
→ Planner
→ PlanGraph
→ Scheduler
→ ParallelExecutor
→ Model / Tool / RAG
→ RuntimeEvent
→ EventJournal
→ Observability
→ Trace
→ Final Output
```

不能只新增测试专用入口。

## 三、LocalAgent 改造目标

### 1. Runtime Mode

建议增加：

```text
CHAT_RUNTIME_MODE=coordinated|legacy
```

规则：

- 在请求开始前决定使用哪个 Runtime；
- 同一个请求不能双跑；
- Coordinated 失败后不能静默重新走 Legacy；
- Legacy 只作为明确回滚路径；
- 日志必须记录所选 Runtime Mode；
- 不将 Runtime Mode 作为高基数 Metrics Label。

### 2. 默认 API 接入

当前默认 `/api/chat` 仍为 Legacy。

第 23 天至少做到：

- `/api/chat` 可以真实进入 Coordinated Runtime；
  -开发或默认配置优先使用 Coordinated；
  -Legacy 保留显式配置；
  -UI 不需要感知内部两套生命周期；
  -现有文本协议兼容层继续负责输出适配。

### 3. Final Output

验证：

- `[[ORCH]]` 不进入最终回答；
  -Runtime Event 不混入正文；
  -Tool/RAG 安全元数据不污染正文；
  -只有业务 OutputDelta / Final Output 进入用户文本；
  -Generator 关闭后不再追加正文；
  -终态事件唯一。

### 4. E2E Happy Path

至少覆盖：

-普通模型回答；
-知识专家 RAG；
-复杂模拟 Tool；
-只读 Tool；
-并行 Step；
-Model Retry；
-Citation；
-Final Output；
-Journal；
-Metrics；
-Trace。

### 5. E2E Failure Path

至少覆盖：

- Planner 失败；
- Model Provider 失败；
- Circuit Open；
- Tool Validation；
- Tool Outcome Unknown；
- RAG EMPTY；
- RAG FAILED；
- Budget Exhausted；
- Timeout；
- Cancellation；
  -客户端断开；
  -Journal Append Failure。

### 6. Shutdown Lifecycle

统一关闭顺序建议：

```text
停止接受新请求
→ 标记服务 Shutting Down
→ 取消或等待活跃 Run
→ RunRegistry wait
→ Tool Detached Worker wait
→ Retrieval Blocking Executor wait
→ EventChannel close
→ Journal close
→ Metrics flush
→ Trace flush
→ Model Session close
→ 其他 Store close
```

要求：

- 每个阶段有 Grace Period；
  -不能无限等待；
  -超时只记录安全 ID；
  -不能强杀 Python Thread；
  -关闭失败相互隔离；
  -多次 shutdown 幂等。

### 7. 生命周期不变量

每个请求结束时：

- Run 有终态；
  -所有 Step 有合法终态；
  -无 Step 残留 RUNNING；
  -Budget Reservation 为零；
  -RunRegistry 已注销；
  -Generator 已关闭；
  -EventChannel 已关闭；
  -Journal 有唯一 `RUN_COMPLETED`；
  -Span 全部结束；
  -Metrics 只计一次；
  -Detached Worker 有明确状态；
  -无重复副作用；
  -Legacy 未被重复调用。

## 四、主要产出

- 真实 API Coordinated Runtime 路径
- Runtime Mode Feature Flag
- Legacy Rollback Boundary
- Shutdown Lifecycle
- E2E Happy / Failure Tests
- E2E Migration Document
- `day23_e2e_runtime_result.md`

## 五、重点 Bad Case

1. Coordinated 失败后静默双跑 Legacy。
2. 同一请求创建两个 run_id。
3. `/api/chat` 仍只走 Legacy，但文档宣称已迁移。
4. Client Disconnect 后后台又执行一次。
5. Shutdown 先关闭 Session，Detached Worker 仍在使用。
6. Journal 先关闭，Run 仍在发布终态。
7. Generator 关闭后 Step 仍为 RUNNING。
8. Metrics/Trace Exporter 阻塞 Shutdown。
9. Final Output 混入 `[[ORCH]]`。
10. Runtime Mode 在请求执行中途切换。
11. Legacy 与 Coordinated 共用错误的 CancellationSource。
12. Journal Failure 导致 Tool 重跑。

## 六、验收重点

-真实 `/api/chat` 能走 Coordinated Runtime；
-同一请求只选择一条 Runtime 路径；
-默认或开发配置使用 Coordinated；

-E2E Happy / Failure 路径完整；

# 第 25 天：阶段二最终验收、性能基线与项目总结

- Capability Matrix（能力矩阵）
- Interview Narrative（面试表达）

## 二、最终 Runtime 不变量

### 1. Run / Step

- 每个 Run 必有终态；
  -每个 Step 状态合法；
  -无 Step 残留 RUNNING；
  -Run terminal 唯一；
  -StopReason 与 RunStatus 一致；
  -Plan 静态不可变；
  -运行状态只属于 AgentState。

### 2. Lifecycle

- RunCoordinator 是生命周期 Owner；
  -RunRegistry 最终注销；
  -Generator 最终关闭；
  -EventChannel 最终关闭；
  -Shutdown 幂等；
  -活跃 Worker 有明确清理状态。

### 3. Budget / Retry

- Budget 无 Reservation 泄漏；
  -并发 Reservation 原子；
  -Retry 不超过预算；
  -Fallback 不静默；
  -Model、Tool、RAG 真实调用数准确；
  -Budget Exhausted 不伪装为业务 EMPTY。

### 4. Cancellation / Timeout

- Cancellation Reason first-wins；
  -Deadline 不被阶段 Timeout 延长；
  -取消后不启动新工作；
  -同步 Worker 超时不宣称已停止；
  -Detached Worker 有追踪和清理边界。

### 5. Tool

- Side Effect State 准确；
  -非幂等 Tool 不透明 Retry；
  -幂等 Replay 不重复提交；
  -Outcome Unknown 不自动恢复；
  -Tool 不修改 RunStatus。

### 6. RAG / Memory

- EMPTY 与 FAILED 区分；
  -Citation 与最终 Payload 一致；
  -Source / Chunk 身份稳定；
  -Memory 始终为 `USER_CONTENT`；
  -RAG/Memory 不获得系统指令权限；
  -检索失败不伪造“未找到”。

### 7. Event / Journal

- Event ID 唯一；
  -per-run Sequence 单调；
  -允许合法 Gap；
  -`RUN_COMPLETED` 唯一；
  -Journal Payload 安全；
  -Duplicate 不重复改变状态；
  -Journal 失败不投递；
  -Channel 失败保留 Journal；
  -不宣称 Exactly-once。

### 8. Observability

- Structured Log 字段统一；
  -无用户正文；
  -无高基数用户 Label；
  -重复 Event 不重复计数；
  -Gauge 最终归零；
  -Logger/Metrics 故障不改变业务结果。

### 9. Trace

-每个 Run 一个 Root Span；
-Step/Invocation/Attempt 层级正确；
-并行 Span 为兄弟关系；
-Context 传播到线程池；
-所有 Span 最终结束；
-Trace 不保存敏感正文。

### 10. Snapshot / Recovery

- Snapshot Schema 可验证；
  -Plan Fingerprint 可验证；
  -Corrupted Snapshot fail closed；
  -Snapshot/Journal Sequence 对齐；
  -RUNNING Step 不自动重跑；
  -Outcome Unknown 不自动恢复；
  -Limited Replay 不调用真实 Model/Tool/RAG；
  -不宣称完整 Event Sourcing。

### 11. 默认入口

-至少一条真实 API 使用 Coordinated Runtime；
-同一请求不双跑；
-Legacy 回滚边界明确；
-`[[ORCH]]` 不污染 Final Output；
-Shutdown 生命周期完整。
