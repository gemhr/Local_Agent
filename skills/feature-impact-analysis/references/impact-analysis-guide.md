# 影响机制与测试指南

## 依赖与生命周期
从变更资源向历史消费者追踪，而非罗列所有功能。记录分配、写入、交付、生产完成、消费完成、释放和复用的顺序；生产完成并不必然意味着消费完成。
共享 Buffer 或公共内存中的引用可能在后续写入后读到不同内容；判断必须有共享关系、释放策略和消费时点的证据。资源所有权不明时，提出具体问题，不自行假设引用计数或同步保护。

## 独立副本与反证
确认副本在何时建立、是否完整、之后是否仍引用原资源；仅有“复制”字样不能证明完全独立。若消费者使用独立资源、已在释放前消费完成或存在明确有效的生命周期保护，应将其列为反证并缩小影响范围。某一路径安全不代表其他消费者也安全。

## 证据关联
每个影响候选关联到历史功能、变更机制、触发条件、支持原文和反证。检索命中仅用于定位，精确读取后才使用 EVIDENCE_READ；任务中已有资料按 TASK_INPUT 引用。引用版本和摘要使用实际原值，不从记忆补造。

## 黑盒测试设计
先确认环境与历史功能前置条件，再安排“产生数据 → 交付消费者 → 触发新生命周期行为 → 后续资源使用 → 消费并观察”。选择真正跨越风险窗口的操作，不依赖任意 sleep 或读取内部实现变量。
对照旧策略和新策略的可观察结果，覆盖正常路径及一个关键风险窗口；独立副本可作为对照。具体 operations 必须符合现有工具/报告支持的操作合同。
核对历史用例的实际步骤与观察点：只写了功能名称或通过标签，不能证明覆盖了延迟窗口。给出覆盖缺口及补测目的；测试建议不是已经执行通过的结果。


## 公开操作合同

当前格式与执行语义以 `core/feature_impact/resource_simulation.py` 的 `validate_operations()` / `execute()` 为准。下表解释现有合同，不定义新 Schema。
`operations` 是长度 1–40 的列表；每项为对象，`request_id` 为非空字符串，字段集合必须与表中完全相同，不允许额外字段。

| action | 必需且仅允许的字段 | 含义与限制 |
| --- | --- | --- |
| SUBMIT | action, request_id, payload | 提交请求；payload 必须存在，格式校验不额外限制其 JSON 形状 |
| DELIVER | action, request_id, mode | 交付消费者；mode 仅为 SHARED、COPY、INDEPENDENT |
| COMPLETE | action, request_id | 标记生产完成，不表示消费完成 |
| CONSUME | action, request_id | 已交付消费者消费并产生报告，不需额外上报动作 |

没有 REPORT、ARCHIVE、READ 动作，也没有 window 操作字段。结算窗口、归档、读取观察点等含义放在 `preconditions`、`observation`、`expected` 中；报告层 `policy` 只能为 OLD 或 NEW。

### 顺序与覆盖

- SUBMIT 的 request_id 不重复。资源占用时新请求可能排队；排队不等于已分配，不能对未分配请求直接 DELIVER/COMPLETE。
- DELIVER/COMPLETE 必须指向实际分配到当前资源 generation 的请求。每个请求只交付一次；CONSUME 只能作用于已交付且尚未消费的同一 request_id，不能另起未交付的“归档/读取”请求名。
- 模拟序列结束至少产生一次消费报告，所有已交付消费者都须完成消费。只有生产完成但没有消费，不构成完整观察。
- 共享引用用 SHARED；副本或独立资源对照须实际使用 COPY/INDEPENDENT，不能只改测试名称而仍用 SHARED。
- 延迟消费风险窗口必须体现为交付后、生产完成与可能的后续资源使用之后再消费。已在之前 CONSUME 的请求不能靠额外虚构 REPORT 动作变成晚消费。
- OLD/NEW 释放条件不同；根据当前策略检查后续写入是已获资源还是仍排队，不把两策略的顺序语义写成相同。观察预期应与选择的 policy 一致。

生成前逐项核对字段、请求关联、交付/消费和风险窗口。`validate_operations` 只检查格式，不执行模拟器，也不保证合法格式的任意序列都可执行或必然出现预期结果；不得声称建议已经运行通过。
